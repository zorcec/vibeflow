Kanban CLI behind the shared operation (ticket 453c7465, P7 kanban
increment, last piece). New `core/operations/kanban.ts` owns `startKanban`
(port/host/dev/quiet/noCtrlCHint assembly, dry-run preview, bind-failure
mapping to KANBAN_PORT_IN_USE/KANBAN_START_FAILED) behind injected ports so
unit tests drive fakes instead of real listeners; the `vibeflow kanban` CLI
handler keeps flag parsing, root resolution/announcement, browser opening
(`--no-open`), changelog chrome and exit codes and now routes through it,
and the `start_kanban` MCP tool shares the same path unchanged. The
kanban singleton (`server/kanban-server.ts`) takes `--dev` (explicit opt-in,
forwarded to `serve()`) plus the renderer's banner switches
(`quiet: false`, `noCtrlCHint`) — coalescing is untouched, so a second
invocation reuses the first instance and never starts a second server or
renegotiates the port. No behaviour change on success paths; a failed CLI
start now prints a clean `✗` refusal (exit 1) instead of an unhandled stack.
