Clone mode (ticket 4efaa878): a task created while logged in (`tasks --add` against your workspace) is now ALSO persisted in the local `.vibeflow` store as its normal `.json` record, so the local copy exists for grep/diff/inspection offline and the two stay identical. The clone is written from the record the server ACCEPTED — the create response carries it on an explicit `record` member and the CLI persists that object verbatim (no mapper, no invented `description ""` / `selector "/"` / stamped author / forced `comments []` / `files []`, which hashed differently from the stored raw). Only the two load-bearing local keys are added when the accepted record lacks them (`sortKey` for board order minted above the store ceiling, `created` from the response `createdAt` for the date-subdir path — same rule as pull imports, converging after one push). Against an older server with no `record` member the CLI falls back to the response-view mapper but warns loudly on stderr that the clone is reconstructed, never exact. Identity is the accepted id, so `push` sees the clone as existing and `pull` is a byte-no-op; online delete still drops the local record; a failed online create returns before any local write; online patch never rewrites the clone.
